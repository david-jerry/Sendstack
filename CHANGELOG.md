# Changelog

All notable changes to Sendstack are documented here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project uses [Semantic Versioning](https://semver.org/). Entries are
added under **Unreleased** as they land — see
[CONTRIBUTING.md](CONTRIBUTING.md#changelog-and-attribution) — and a release
turns that section into a dated, versioned one.

## [Unreleased]

### Added

- `test/architecture.test.ts` fails when a Server Action, API route or background job has no owner in the ownership matrix. A matrix is only worth writing down if it cannot silently go stale, and the way it goes stale is a new API route nobody notices belongs to nobody — which is a new place a send can happen. It reads the matrix out of `docs/ARCHITECTURE.md` rather than hardcoding a list, and needs no glob dependency. ([@jdavid](https://github.com/jdavid))
- A pull request template asking the four things a reviewer of a bulk-email system has to establish anyway: which flow the diff reaches, which context owns the code, which invariants were verified and how, and which test would fail if the change were undone. ([@jdavid](https://github.com/jdavid))
- A bounded-contexts section in `docs/ARCHITECTURE.md`: an ownership matrix mapping every Server Action, API route and job to one of eight contexts with its aggregate, invariants and proving tests, plus the decision record for what was rejected (a per-context rewrite, a realtime outbox, verification at sign-in). `docs/DDD-EXECUTION-PLAN.md` sequences the refactor into five sprints of ticketed work. ([@jdavid](https://github.com/jdavid))
- One Identity gate for every send-capable action, `assertCanSend` in `@sendstack/auth`, called by compose, reply, send-now and schedule. Its policy is `"unenforced"` by decision — enforcing verification at sign-in would lock out the operator configuring the very sender that delivers the verification mail — so today it always allows; changing that is one value, not four `if`s. Refusals are recorded in the new `policy_decisions` table (migration 0020); allows are not, because that would be an unbounded write on every send. ([@jdavid](https://github.com/jdavid))
- Upload your own HTML email templates in Settings → Email. They appear in the Design picker beside the four built-in designs when composing a message or creating a campaign, are previewed in a sandboxed frame, and come with two copy-to-clipboard prompts for having one written or adapted by an AI assistant against the exact placeholder contract the renderer fills in. Merge fields now support `{{#if name}}…{{/if}}` blocks. ([@jdavid](https://github.com/jdavid))

### Changed

- `outbound_messages.last_event` stores one dialect. It held Resend's prefixed webhook names *and* `emails.list()`'s unprefixed ones, so three readers stripped a prefix that might not be there. Both writers now normalise at ingestion, migration `0019` rewrites the rows written before, and a `CHECK` constraint makes a fourth writer fail loudly rather than quietly reintroduce the drift. ([@jdavid](https://github.com/jdavid))
- The thread view costs three database round trips instead of five, and marking a thread read costs one instead of two — the thread key is resolved inside the write statement, and the reads that do not depend on each other no longer wait on each other. The statement count is unchanged; what changed is how many of them block. ([@jdavid](https://github.com/jdavid))
- **One send pipeline for compose and replies.** The attachment query, the claim, and both status writes were duplicated between `sendSingleEmail` and `sendMessage`, byte for byte — and the claim's `WHERE status <> 'sent'` is the only thing between a double-clicked Send and a second real email. It had already gone missing from one copy once. What legitimately differs between a composed message and a reply is everything before the claim, and none of it moved. Removing the guard from the single shared copy now fails both paths' replay suites. ([@jdavid](https://github.com/jdavid))
- Inngest payloads are validated on **receive**, not only on send. `eventType` covers publishers; a function's `event.data` was typed rather than checked, and events arrive from places that are not a publisher — a hand-edited dashboard replay, or an event queued before a deploy. The continuation counter was the dangerous one: a non-number makes the hand-off arithmetic produce `NaN`, which compares false against every bound and queues another pass for ever. ([@jdavid](https://github.com/jdavid))
- The realtime contract has producer-side tests. Consumers already parsed on receipt, so a stale shape was dropped rather than trusted — but a field removed from a *publisher* still compiled, still published, and was then silently discarded, which looks like "realtime stopped working" with no error anywhere. One fixture per event type now fails if the schema and the publishers disagree in either direction. ([@jdavid](https://github.com/jdavid))
- `nameField` title-cases, which its docstring already claimed. `normalizeName` ran after parsing in four separate actions, so the schema validated one value and the database stored another — and the admin account's name, which uses the same field with no post-parse call, was stored exactly as typed. Renaming yourself later went through a fifth spelling that skipped the casing entirely. ([@jdavid](https://github.com/jdavid))
- Rules that existed in more than one place now exist in one. The `email.` prefix strip on a stored delivery event (`bareEvent`, three copies), the keyset seek predicate every list query shares (`seek`, three copies), the "do not send to this person" SQL (`isUnsendable`, four copies), the search-param-to-`undefined` collapse in the list routes (`asOptional`, four copies), the service worker's cache prefix (two files with nothing checking they agreed), `${n} thing${n === 1 ? "" : "s"}` (`plural`, ten copies across six components), the brand colour's hex pattern and default (`HEX_COLOR_PATTERN`, `DEFAULT_BRAND_COLOR`, three and four copies), and the app-URL join (`absoluteUrl`, six copies — five of which stripped a single trailing slash and so left the second one behind). The brand default cannot share a declaration with `app_settings.primary_color`'s column default, because a migration is SQL, so a test in `packages/db` fails if the two diverge. ([@jdavid](https://github.com/jdavid))
- `@sendstack/email` exports `ResendNotConfiguredError`, so the reconcilers narrow their `catch` on the class instead of matching the text of a message. Rewording that message used to widen both catches back to swallowing every database fault, with nothing failing. ([@jdavid](https://github.com/jdavid))
- Every package has a `README.md`, and the root one indexes them with a dependency graph verified against the manifests. Twenty-three previously undocumented exports across `auth`, `config`, `email`, `redis` and `shared` carry a docblock saying why they are built the way they are. ([@jdavid](https://github.com/jdavid))
- The `templates` table, unused since 0000_init, now stores uploaded templates; migration 0014 reshapes it and clears any rows placed there by hand. `campaigns.custom_template_id` records which uploaded template a campaign uses. ([@jdavid](https://github.com/jdavid))
- Migration 0016 adds `contacts_created_idx (created_at DESC, id DESC)`, matching the keyset order the contacts list pages by. On 200,000 rows with 50,000 sharing a timestamp — what a CSV import produces — a page went from 49.8ms and a full sort of the collision group to 0.133ms and no sort. ([@jdavid](https://github.com/jdavid))
- Migration 0015 adds the constraints three of these fixes depend on: a unique index on `(inbound_email_id, provider_attachment_id)`, `outbound_messages.client_key` with a unique index, sort indexes for the Sent, Drafts and Campaigns lists, and `campaigns.list_id` moved to `ON DELETE RESTRICT` so a deleted list can no longer turn a campaign into a send to every contact. ([@jdavid](https://github.com/jdavid))
- Delivery-event handling has one definition. What a provider event means and the "never move backwards" status ladder live in `@sendstack/shared`, and the SQL `CASE` the webhook route and the sent-mail reconciler run is generated from it. The three previous copies had already diverged: the route dropped `email.delivery_delayed` entirely, and a complaint against a one-off message was recorded as a clean send in one place and a failure in the other. ([@jdavid](https://github.com/jdavid))
- Database enums, page sizes, the password minimum and the `AUTH_SECRET` minimum are each declared once in `@sendstack/shared` and imported everywhere else, replacing between two and five copies apiece. ([@jdavid](https://github.com/jdavid))
- The contacts page shows capped counts, rendered `20k+` past the cap like the sidebar badges, instead of counting every contact and every suppression on each load. ([@jdavid](https://github.com/jdavid))
- CI runs the database-backed suites. The `check` job gets a Postgres service and applies migrations before the tests, and the gate those suites share now *fails* instead of skipping when `CI` is set with no `DATABASE_URL` — a suite that silently does not run reported green over sixteen queries that never executed. ([@jdavid](https://github.com/jdavid))

### Deprecated

### Removed

- `generateVapidKeys` from `@sendstack/email`, which had no callers and a docstring naming a script that uses the `@sendstack/pwa` implementation instead. ([@jdavid](https://github.com/jdavid))
- `contacts_created_at_idx`, made redundant by migration 0016's `(created_at DESC, id DESC)` index and dropped in migration 0017. It cost write throughput for nothing. ([@jdavid](https://github.com/jdavid))
- A second `setThreadStatus` in `actions/inbox.ts` that nothing imported — the toolbar and the row menu both use the one in `actions/thread.ts` — along with the private `threadUnread` counter beside it and a duplicate `threadKeyOf`. Both actions now share one arbitrated write. Also `RichEditorHandle`, which had no importers and no `forwardRef` to be the handle of. ([@jdavid](https://github.com/jdavid))
- Dead code: `replyToThread` (no callers, and it sent without writing an outbound row or checking suppressions), `listThreads`, `countUnread` (an uncapped count), `listOutbound`, and `SEND_CONCURRENCY`. ([@jdavid](https://github.com/jdavid))

### Fixed

- **CI failed on every push.** `pnpm lint` exited non-zero on one pre-existing error — a synchronous `setState` inside an effect in the add-to-list modal, which the React compiler rejects. The spinner flag is now derived from which search term the loaded rows belong to, which is also what the condition actually is: what is on screen is not an answer to what was typed. ([@jdavid](https://github.com/jdavid))
- **A reply could be sent to a contact the campaign paths refuse.** "Do not send to this person" is two conditions — a live suppression row, *or* a contact whose status has left `active` — and `assertNotSuppressed` asked only the first while both campaign paths asked both through `isUnsendable`. So a contact recorded as bounced with no suppression row was refused a campaign and accepted for a reply. Reachable whenever an operator deletes a `manual` or `unsubscribe` suppression, since the contact's status stays where the webhook left it. ([@jdavid](https://github.com/jdavid))
- **A file attached before typing left the draft detached from its conversation.** `attachFile` creates the row when someone attaches before the first keystroke, and it wrote `kind: 'compose'` with no parent whatever thread the composer was open in. `saveDraft` overwrote both on the first keystroke, so it only survived the attach-then-close path — and then the draft sat in Drafts with no way back to the thread it was written in. ([@jdavid](https://github.com/jdavid))
- **A reply whose stored text was empty sent an empty plain-text part.** The two send paths spelled the fallback differently and the reply used `??`, so `text: ""` was passed through rather than converted from the HTML. A message whose plain-text alternative is blank renders as nothing at all in a text-only client. ([@jdavid](https://github.com/jdavid))
- A second bounce's push notification named a reason the thread view did not show. `error` is written first-wins, so the notification now reads the row like the realtime publish beside it. ([@jdavid](https://github.com/jdavid))
- **A reply could be sent twice.** `compose.ts` minted a browser `clientKey` and upserted on the unique index; `thread.ts` had its own draft write that ignored it, so a double-clicked Send inserted a fresh row each time and two sends went out under two claim keys the provider could not collapse. Both paths now share `upsertKeyedDraft`, which lives in `lib/queries/outbound.ts` because a `"use server"` module cannot export an internal write without publishing it as an endpoint. Proven by a test that presses Send three times, and again with two presses overlapping, and asserts one row and one provider call. ([@jdavid](https://github.com/jdavid))
- **The compose dialog had the same hole online.** The browser-minted key existed only on the offline queue path; `sendSingleEmail` carried none, so `saveComposeDraft` skipped the keyed upsert entirely and two tabs inserted two rows. Both paths now pass the same key, which also means a send queued offline and retried online resolves to one row instead of two. ([@jdavid](https://github.com/jdavid))
- **A retried delivery event could relabel a clicked message "Delivered".** The webhook guarded `last_event` with the *status* ladder, which collapses `sent`, `delivery_delayed`, `delivered`, `opened` and `clicked` into one rung and so cannot order them — and Resend's retries each carry a fresh `svix-id`, so no dedupe guard applied either. There is now an event-level guard as well, reusing the existing recipient funnel rank rather than adding a second ladder, and the two are ANDed: the status half is what stops a late event landing on a message our own send path failed, the event half is what orders the sent band. Each half has its own failing test if removed. ([@jdavid](https://github.com/jdavid))
- **A stale Sync page could undo a recorded bounce.** `emails.list()` is eventually consistent, and the reconciler assigned `last_event` with no guard at all while putting `status` through the shared ladder — so a list page still reporting `delivered` left `status='failed'` beside `last_event='delivered'`, which the thread view renders as a red failed bubble carrying a green Delivered badge. ([@jdavid](https://github.com/jdavid))
- **Every thread view threw `bareEvent is not a function`.** A client component called the shared helper to strip the `email.` prefix, and Turbopack resolved that import to a module fragment where the function was undefined. The column now holds one dialect, so nothing needs stripping on read. ([@jdavid](https://github.com/jdavid))
- **A late open relabelled a bounced reply as opened, on screen only.** The webhook's SQL ladder kept `outbound_messages.last_event` on the bounce, then the realtime event beside it broadcast the *incoming* event regardless. The thread view prefers the live value to the server-rendered row, and the store's own ladder can only compare one live event against another — so for a bounce that arrived before the page loaded, a late `email.opened` had nothing to be refused against. It won, the error cleared, and Postgres was right the whole time. The publish now carries the event and error the row actually holds. ([@jdavid](https://github.com/jdavid))
- **The unread badge counted messages while its neighbours counted conversations.** `folderCounts` counted rows in `inbound_emails` for Unread and distinct threads for Archived and Spam, and all three open a list with one row per conversation — so a three-message thread showed as 3 over a list of 1. Unread now counts conversations, the realtime delta for a thread going read is `-1` rather than one per message, and the store increments once per conversation instead of once per arriving message. The badge also stopped losing a point every time a conversation was archived after being read, or restored from Archive: the delta is now derived from the rows the `UPDATE` actually moved out of `unread`, in one statement, so a repeat call is worth nothing and a thread that held nothing unread reports nothing. Measured on 40,000 messages: 0.478ms when 800 are unread, 23.7ms when all of them are. ([@jdavid](https://github.com/jdavid))
- **The unread badge could disagree with the database for a whole session.** `RealtimeBridge` reseeded from `folderCounts` only when the *number* changed, which the old row-counting badge guaranteed on every arrival. Counting conversations removed that guarantee — a second message in an already-unread thread leaves the count identical — so the one mechanism that reconciles the live store against Postgres stopped firing in exactly the case where the store had drifted. It now reseeds on every server render, and adopting a server count discards the live bookkeeping behind it. ([@jdavid](https://github.com/jdavid))
- **Sync reported "Up to date" while a hundred message bodies were still missing.** `SyncResult` separated bodies fetched inline from bodies handed to the hydrate job, and nothing carried the second number to the caller. The toast now reports both, in the tense that matches: what it re-fetched, and what is still coming. It also no longer says "1 message body" for any count. ([@jdavid](https://github.com/jdavid))
- **No campaign batch could send at all.** The recipient claim joined `contacts` on the statement's own update target from inside its `FROM` clause, which Postgres refuses outright, so every batch threw before a single message was built. It typechecked, it built, and no test executed it. The join now reads the claimed slice's `contact_id`, and the claim is exercised against a real Postgres so this cannot recur silently. ([@jdavid](https://github.com/jdavid))
- **Scheduled campaigns never sent.** The cron claimed a due campaign by moving it to `sending`, and the job it then triggered refused any campaign already in that state, so every scheduled send failed at its first step. The claim now belongs to the job, guarded on `started_at IS NULL`, which also makes a manual send and a cron tick landing in the same minute materialise once. ([@jdavid](https://github.com/jdavid))
- **Cancelling a campaign did nothing.** The action emitted an event, and the job it woke required the campaign to already be `cancelled` — a status nothing set. The action now claims that transition and refuses a campaign that has already gone out. ([@jdavid](https://github.com/jdavid))
- **Pausing a draft could report a send that never happened.** `pauseCampaign` had no status guard, so a paused draft could be resumed into `sending` with no recipients materialised, where the completion check marked it `sent`. Both pause and cancel are now single conditional statements that answer instead of silently doing nothing. ([@jdavid](https://github.com/jdavid))
- **A provider timeout permanently failed a hundred recipients.** A transport-level error marked every message in the batch `failed` and moved on, even though Resend may well have accepted them; later delivery webhooks were then blocked by the monotonic ladder, so those recipients stayed wrongly failed forever. The batch now throws so the job retries with backoff. ([@jdavid](https://github.com/jdavid))
- **A recipient could move backwards.** The worker's post-send write was unconditional, so a `delivered` or `bounced` webhook processed while the row was still `sending` was overwritten back to `sent`. ([@jdavid](https://github.com/jdavid))
- **A suppression could be bypassed by capitalising the address.** Every row in `suppressions` is stored normalised and Postgres compares text case-sensitively, but the reply composer stored the address exactly as typed — so a reply to `Ada@Example.com` sailed past a suppression on `ada@example.com`. Replies now normalise and split at the boundary like the compose form, and the shared check normalises again as a backstop. ([@jdavid](https://github.com/jdavid))
- **Claim-time suppression was narrower than materialisation-time.** The re-check inside each batch consulted only the suppressions table, so a contact whose status moved off `active` after materialisation was still mailed: a manual deactivation, or any path recording a bounce on the contact without also writing a suppression row. Both checks now apply the identical condition. ([@jdavid](https://github.com/jdavid))
- **Suppression was not checked on every send path.** A campaign only consulted the list when its recipients were first materialised, which can be hours or days before the send, so a complaint or hard bounce arriving in between was mailed anyway; it is now re-checked inside each batch claim. The inbox reply composer never checked at all. Every one-to-one path now goes through one `assertNotSuppressed` helper. ([@jdavid](https://github.com/jdavid))
- **A failed webhook handler lost its work permanently.** The dedupe row was committed before the side effects ran, so a handler that threw left a row that deduped every retry while the suppression or status update it existed to perform never happened. The row and the work are now one transaction, and realtime publishes and push notifications are held until it commits. ([@jdavid](https://github.com/jdavid))
- **Re-hydrating an inbound message duplicated its attachments.** There was no unique index for `ON CONFLICT` to catch, and double hydration is routine — the webhook-triggered job and the hourly reconciler overlap on any message whose body has not landed yet. ([@jdavid](https://github.com/jdavid))
- **An offline send could go out twice.** The provider idempotency key came from a draft id the server minted, so a queued send with no draft yet minted a new row and a new key on every replay, and a first attempt whose response was lost was re-sent. The browser now generates the key before queueing, a unique index makes it the message's identity, and a replay of an already-sent message returns the original answer without touching the provider. ([@jdavid](https://github.com/jdavid))
- **A setting cleared in Settings came back from the environment.** Clearing wrote a null, which the resolver read as "never configured" and re-seeded from `REDIS_URL`, `CLOUDINARY_*` or `RESEND_API_KEY` — contradicting the documented rule that the database always wins. A cleared value is now a tombstone, and Settings labels it "cleared here". ([@jdavid](https://github.com/jdavid))
- **Every setup Server Action was callable by anyone, forever.** Server Actions are invoked by id independently of the page that renders them, so on a fully configured instance an anonymous request could overwrite `.env.local`, swap the Resend key and route magic links through an attacker, or change the app URL that anchors auth callbacks and passkeys. Each action now refuses unless setup is genuinely in progress. ([@jdavid](https://github.com/jdavid))
- **Pages queried the database before the layout could redirect.** Next renders a layout concurrently with the pages and layouts beneath it, so an anonymous request reached the queries and their results reached the RSC payload. Every page and list component that reads data now gates itself. ([@jdavid](https://github.com/jdavid))
- **N+1 patterns in the audience and sync queries.** The contacts list ran four correlated subqueries per row, the group and list pickers ran one count per row with no limit at all, and the sent-mail reconciler ran between two and six queries per message. Each is now a bounded number of statements, verified with `EXPLAIN (ANALYZE, BUFFERS)` through the app's own query builder. ([@jdavid](https://github.com/jdavid))
- **The plain-text part of a campaign omitted the unsubscribe link and postal address**, because a stored `text` column derived from the body alone was preferred over the renderer's output. ([@jdavid](https://github.com/jdavid))
- A webhook that won the Redis dedupe claim and then failed to write to Postgres was dropped for 24 hours on retry, but only when Redis was configured. The claim is now released on failure so the database alone decides what a retry sees. ([@jdavid](https://github.com/jdavid))
- Changing the Redis URL left every open realtime stream subscribed to the old server. Subscriptions are now tracked and ended on reconfiguration, streams are recycled every four minutes so an Upstash stream that ends silently cannot leave a tab deaf, and the browser refetches from Postgres on every reconnect as the architecture doc always said it did. ([@jdavid](https://github.com/jdavid))
- An unreachable Redis blocked webhooks and Server Actions for most of a minute per call. Both transports now run on a two-second connect budget with one retry, and the TCP client backs off for thirty seconds after a failed connect. ([@jdavid](https://github.com/jdavid))
- The realtime stream leaked its heartbeat and Redis subscriber when a write to the client failed without an abort. ([@jdavid](https://github.com/jdavid))

### Security
