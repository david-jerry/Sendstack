# Working on Sendstack

Read [PRODUCT.md](PRODUCT.md) before anything else. It is the specification —
outcomes, core flows, invariants, architecture boundaries and what is explicitly
out of scope. This file is *how* to work; PRODUCT.md is *what* is true.

`apps/web/AGENTS.md` is **generated by `next dev`** and re-created on every run.
Never put project rules there; they belong here.

---

## 1. Ask before you act

**Investigate freely. Change nothing until the ambiguity is resolved.**

Reading, grepping, running tests, and reading `EXPLAIN` output are not actions —
do them first, so the questions you ask are specific. Writing, editing, deleting,
installing, migrating and deploying are actions, and they wait.

Before the first action on any request, ask yourself: *is there more than one
reasonable reading of this?* If yes, stop and use **AskUserQuestion**:

- **Batch every question into one call.** Four separate round trips to resolve
  one task is worse than not asking.
- **Make options concrete.** Name files, show an ASCII mockup, quote the two
  candidate schemas. "Which approach?" is not a question; a preview the user can
  compare is.
- **Never ask what the repository can answer.** If the answer is in the code,
  the schema, PRODUCT.md or the git history, go and read it.
- **Say what you will do with each answer**, so a wrong guess is visible before
  it costs work.

Proceed without asking only when *all* of these hold:

1. the request names the change precisely (a typo, a rename, a stated value);
2. it touches one file, or one obvious set of files;
3. nothing about it contradicts PRODUCT.md;
4. it is continuing a plan the user already approved in this conversation.

**Two situations always require a question, regardless:** anything that changes
a database schema or a public contract, and anything the user could reasonably
have meant to apply to a different surface (mobile vs desktop, one route vs a
route group, the package vs the app).

When you find an uncertainty mid-task: finish everything that does not depend on
it, then ask. Do not down-scope silently and do not guess and continue.

## 2. Propose the agent before you spawn it

The agents in [.claude/agents/](.claude/agents/) are specialists. Use them —
and **name your choice, with your reasoning, alongside the clarifying
questions**, before spawning anything. The user picks.

| Work | Agent |
| --- | --- |
| Slow query, index or plan | `database-optimization` |
| Query shape, schema, service boundaries | `backend-architect` |
| Layering, SOLID, package boundaries | `architect-review` |
| Quality/security/perf pass over a diff | `code-reviewer` |
| Narrow security question | `security-auditor` |
| A bug with a stack trace or a repro | `debugger` |
| Failures across services, cascades | `error-detective` |
| Next.js App Router specifics | `nextjs-architecture-expert` |
| React/TS implementation | `frontend-developer`, `typescript-pro` |
| Profiling, caching, load | `performance-engineer` |
| Docs from code | `documentation-expert`, `technical-writer` |

Do it in the main session instead when the task is small, sequential, touches
files you are already editing, or needs the conversation's history to make
sense. A subagent has overhead and, crucially, no memory of this conversation.

**Skills** in [.claude/skills/](.claude/skills/) load domain rules into the
turn — `drizzle-orm-expert`, `tanstack-query-expert`, `nextjs-app-router-patterns`,
`react-best-practices`, `progressive-web-app`, `zod-validation-expert`. Invoke
the relevant one *before* writing code in its area, not after a review says you
should have.

## 3. Handoffs

There are two kinds, and they work differently. Do not confuse them.

### To a subagent (within this session)

A subagent starts in a **fresh context window**. It receives its own system
prompt, every level of `CLAUDE.md`, a git-status snapshot, and the delegation
prompt you write. It receives **none** of the following:

- this conversation's history;
- the files you have already read;
- the skills you have already invoked;
- anything another subagent discovered.

So **the delegation prompt is the handoff.** It must stand alone. Include the
paths that matter, the constraint being honoured, the decision already taken,
and what "done" looks like. A prompt like "fix the N+1 we discussed" hands over
nothing — the subagent has never heard of it.

**Subagents cannot talk to each other.** Anthropic is explicit about this:
results come back to the main conversation, and the next stage is delegated from
there with the previous result folded into its prompt. If a stage needs a
sibling's output, *you* carry it across. Do not design a pipeline that assumes
agent-to-agent messaging.

What returns is the subagent's final report plus an agent id. Use
**SendMessage** with that id to continue the same subagent with its history
intact; a fresh `Agent` call starts from nothing again.

Sequence multi-stage work explicitly — explore, then plan, then execute —
presenting the plan for approval between the second and third. Each stage gets a
prompt built from the last stage's report.

### To another session (across time)

Use the installed **`/handoff`** skill. It writes a document a fresh agent can
resume from, in the OS temporary directory, referencing artifacts by path rather
than restating them. Do not hand-roll a substitute for it.

## 4. Never drift from PRODUCT.md

Before starting, name which core flow or invariant the work touches. If you
cannot, that is the signal to ask rather than to begin.

Treat these as walls, not preferences:

- Postgres is the source of truth; realtime is latency, never correctness.
- Sends are idempotent and duplicate-safe. Webhooks tolerate at-least-once.
- Suppression is checked on **every** send path.
- Addresses are normalised at ingestion boundaries.
- Inbound HTML is never trusted app content.
- Client components never reach a provider; they go through a Server Action or
  an API route.
- Shared contracts live in `packages/shared`; constraints live in the
  `packages/db` schema and its migrations.

If a request appears to conflict with an invariant, **say so in one or two
sentences and ask** — do not quietly satisfy the request and break the
invariant, and do not refuse. PRODUCT.md's "Out of Scope" list is the same
kind of wall: no silent rewrites, no new package where an existing one extends
safely.

## 5. Simple, non-redundant code

**Before writing anything new, search for it.** A helper, hook, component or
query that already exists is the one to extend. Two implementations of one rule
is the defect — the second copy is where the drift starts.

- One definition per rule, in one place. A number that must agree in two
  packages (a password length, a cache prefix, a page size) is declared once
  and imported.
- Delete what nothing imports. Check for entry points first: Next file
  conventions, `package.json` scripts and CLI bins are referenced by name, not
  by import.
- Prefer the smaller change. A new file needs a reason beyond "it felt tidier".
- Match the surrounding code's idiom, naming and comment density.

## 6. Every block carries a docstring

Every exported function, component, hook, route handler, job and non-obvious
internal gets a docblock. **Say what it is for and why it is built this way —
never what the code plainly does.**

The test of a good docstring: it explains something the reader could not have
worked out from the lines beneath it. The failure mode it prevents. The
alternative that was rejected and why. The measurement that settled it.

```ts
/**
 * Whether the two halves of a VAPID pair belong to each other.
 *
 * The public point is **derived** from the scalar rather than imported
 * alongside it. That distinction is the whole test: `createPrivateKey` will
 * happily import a JWK whose `x`/`y` belong to a different key and echo them
 * straight back, so a comparison built on it returns true for exactly the
 * mismatched pair it was written to catch.
 */
```

Comment inline where a line looks wrong but is right. Where a magic number
comes from. Where an ordering is load-bearing.

## 7. Zero N+1, zero duplicity, zero races — proven, not assumed

These are the three failure classes this product cannot absorb. Each has a
proof obligation, and "I looked at it carefully" is not one of them.

### N+1

- Every list and batch path is one query, or a bounded number. Never one per
  row.
- **Prove it with `EXPLAIN (ANALYZE, BUFFERS)` against real data.** A `SubPlan`
  with `loops=` above 1, or a per-row `Seq Scan`, is the bug.
- Run the plan through the **application's own query builder**, not SQL retyped
  into `psql`. A missing comma between CTEs survives retyping and fails at
  runtime; that has happened here.
- Set-based operations for materialisation and status updates. `IN`/`ANY` and
  `INSERT … SELECT`, not a loop.
- Counting an unbounded table is a bug at scale: cap it, and say the count is
  capped.

### Duplicity

- Every write reachable twice is idempotent. Webhook retries, replayed queue
  entries, double-clicked buttons, a job the scheduler fires twice.
- Enforce it in the **schema** — a unique index plus `ON CONFLICT DO NOTHING`
  or `DO UPDATE` — not in application logic that races with itself.
- Provider sends carry an idempotency key.
- **Prove it with a test that runs the handler twice** and asserts one row and
  one side effect.

### Race conditions

- Never read-then-write across an `await` without the database arbitrating.
  Claim work with `UPDATE … WHERE status = 'pending' … RETURNING`, not
  `SELECT` then `UPDATE`.
- Status transitions are monotonic: an out-of-order event must not move a row
  backwards.
- Distributed locks and claims go through Redis or a row lock, and both must
  behave correctly when Redis is absent — it is optional.
- Client-side: an in-flight request must be cancellable or its stale response
  discarded. Optimistic state is reconciled against the server's answer.

## 8. Before saying it is done

Run these from the repository root. They are the scripts in the root
`package.json`; none of them takes a file argument, on purpose.

```bash
pnpm test        # vitest run — the whole suite, not the file you touched
pnpm typecheck   # every package, not just apps/web
pnpm lint        # if the problem count rose, it rose because of you
pnpm build       # anything touching a route, the service worker or config
```

New guard or invariant? **Break it on purpose and watch the test fail.** A test
that has never failed has not been shown to test anything — a "hydrates without
a mismatch" test passed here while rendering identically on both sides and
proving nothing.

Report what you actually ran and what it said. If a step was skipped, say which
and why. Never describe work as verified because it typechecked.
